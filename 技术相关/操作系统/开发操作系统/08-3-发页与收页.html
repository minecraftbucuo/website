08 · 内存管理（三）：发页与收页

上一篇：08-2-位图分配器。位图账本建好了，家底也能报出来
（1DF95 frames total, 1CD0E free）——但分配器还只会"统计"，不会"分配"。
本篇给它装上 alloc_frame/free_frame，再做一场每个数字都能当场验算的实验。

动手六：alloc_frame / free_frame（mm.rs）

先明确这两件事分别是什么：

  • 分配 = 在位图里找一个值为 1 的位（空闲页）→ 清成 0（标成已分配）→ 返回这页的物理地址
  • 收回 = 把那一位重新置 1，完事

代码加在 mm.rs 的 stats 之后（文件末尾）：

/// 发一页：返回这页的起始物理地址。没空页返回 None
pub fn alloc_frame() -> Option<u64> {
    let a = ALLOCATOR.get().as_mut()?;
    let bitmap_len = (a.frames as usize + 7) / 8;

    // 从游标处往后找第一个非零字节（非零 = 里面有空闲位）。
    // next_hint 记的是页号，一个字节管 8 页——先除以 8 换算成字节下标
    let mut i = (a.next_hint / 8) as usize;
    while i < bitmap_len {
        let byte = unsafe { *a.bitmap.add(i) };
        if byte != 0 {
            // trailing_zeros：最低位的 1 在第几位——顺手的位运算找位法
            let pfn = (i as u64) * 8 + byte.trailing_zeros() as u64;
            a.set_used(pfn);
            a.next_hint = pfn; // 游标跟上
            return Some(pfn * PAGE_SIZE);
        }
        i += 1;
    }
    None // 位图里再没有 1：内存发完了
}

/// 收回一页（参数是 alloc_frame 当时给的物理地址）
pub fn free_frame(phys: u64) {
    if let Some(a) = ALLOCATOR.get().as_mut() {
        let pfn = phys / PAGE_SIZE;
        a.set_free(pfn);
        // 收回的页排在游标前面的话，游标退回去——
        // 空闲页优先重发，位图前段不会越积越稀
        if pfn < a.next_hint {
            a.next_hint = pfn;
        }
    }
}

逐个说清楚：

返回的是物理地址。alloc_frame 给出的是 pfn * PAGE_SIZE——物理地址，不是虚拟地址。分配器只管物理内存这本账；拿到页的调用方自己决定怎么访问它（内核里通常就是 phys_to_virt 加一下）。这个分工以后一直保持：mm.rs 说物理，别的模块自己翻译。

扫描是两层的。外层逐字节扫，byte != 0 才进内层细看——一个字节 8 位全 0（8 页全满）就一眼跳过，不用逐位检查。全满的位图前段被这层粗扫快速略过，这正是游标存在的意义：i 从 next_hint / 8 开始，前面的字节根本不看。

trailing_zeros 找位。进入内层说明这个字节里至少有一个 1（空闲页），在哪个位？trailing_zeros() 返回"最低位的 1 在第几位"。举例：byte = 0b0010_0100，最低位的 1 在第 2 位 → trailing_zeros() = 2 → 这个字节管的 8 页里，第 2 页空闲。所以 pfn = 字节下标 × 8 + 位号。

free_frame 的游标回退。收回页时把位置回 1；如果收回的页在游标前面，游标也退回去——下次分配优先重发刚收回的页。没有这一步，游标永远只进不退，前面释放的页要等位图后段用完才会轮到。

动手七：分配实验（main.rs）

功能装好了，现在验证。规则先立好：跑之前，先把每个数字预测出来写在本子上——预测对了，说明你对机制的理解和代码一致；对不上，立刻就有线索可查。

先预测

问自己：alloc_frame 连按三次，返回的三个物理地址应该是多少？

推理链条：

  1. 位图放在哪？——from_memmap 自举找的是第一个放得下的 usable 区段的开头。看清单：第一行 1000 +86000 usable，长度 0x86000 = 544KB，远超位图的 15KB → 位图在 0x1000
  2. 位图占 4 页：0x1000 ~ 0x4FFF（第 1~4 页），已被标成"已分配"
  3. 第一次分配 → 第 5 个空闲页 → 页号 5 → 物理地址 5 × 0x1000 = 0x5000
  4. 接着两次 → 0x6000、0x7000（游标顺着走）

预测：alloc 3 frames: 5000 6000 7000。

第二问：把第二页（0x6000）收回，再分配一次，拿到的是多少？——收回后位图第 6 页重新变 1，游标退回页号 6 → 再分配拿回 0x6000。

写代码

在 main.rs 里，frame allocator up 那段打印之后、同一个 if mm::init(...) 分支内：

                    // 现场实验：发页 → 写读验证 → 收回重发
                    let p1 = mm::alloc_frame().unwrap();
                    let p2 = mm::alloc_frame().unwrap();
                    let p3 = mm::alloc_frame().unwrap();
                    serial::print("alloc 3 frames: ");
                    serial::print_hex(p1);
                    serial::print(" ");
                    serial::print_hex(p2);
                    serial::print(" ");
                    serial::print_hex(p3);
                    serial::print("\n");

                    // 往第一页写个魔数再读回来——证明这页真的能用
                    unsafe {
                        let v = mm::phys_to_virt(p1) as *mut u64;
                        v.write_volatile(0x1234_5678_9ABC_DEF0);
                        let r = (v as *const u64).read_volatile();
                        if r == 0x1234_5678_9ABC_DEF0 {
                            serial::print("page write/read ok\n");
                        } else {
                            serial::print("page write/read FAILED!\n");
                        }
                    }

                    // 收回 p2 再发：该拿回同一页（free 生效 + 游标回退的证据）
                    mm::free_frame(p2);
                    let p4 = mm::alloc_frame().unwrap();
                    serial::print("free 2nd frame, realloc got: ");
                    serial::print_hex(p4);
                    serial::print("\n");

三段实验各验一件事：

  1. 连发三页：验证分配顺序和预测的数字
  2. 写读魔数：分配器说"这页给你了"，是真的吗？通过 phys_to_virt(p1) 拿到这页的虚拟地址，写进去一个 64 位魔数再读回来。相等 = 这页物理内存真的存在且可写——分配器没发空头支票
  3. 收回重发：free 之后马上 alloc，拿到 0x6000 就同时证明了两件事——free 真的把位改回 1 了；游标真的退回去了

运行验证

make run

串口在 frame allocator up 之后应多出三行：

alloc 3 frames: 5000 6000 7000
page write/read ok
free 2nd frame, realloc got: 6000

对照预测：三个数字全中，实验完成。

预测对不上了怎么办？先别改代码，按这个顺序查：

  • 数字是预测的 8 倍左右（比如 28000、140000）→ 页号被当成字节下标用了，见下面的踩坑实录
  • 起点不是 5000 → 位图没放在 0x1000，检查 from_memmap 的自举循环
  • page write/read FAILED! → HHDM 偏移不对，或 phys_to_virt 写错了

踩坑实录：×8 大坑

这个实验我们真的踩过，第一版代码跑出来的是：

alloc 3 frames: 5000 28000 140000

第一次 5000 是对的，之后每次跳的步长是 0x8000、0xC000——是预期步长 0x1000 的 8 倍。

原因在 alloc_frame 的扫描起点。第一版写的是：

let mut i = a.next_hint as usize;   // 错：next_hint 是页号！

next_hint 存的是页号（第 6 页就是 6），而 i 是位图的字节下标（一个字节管 8 页）。页号 6 被直接当成字节下标 6 用，相当于从"第 48 页"开始找——起点凭空跳到 8 倍远处。第一次分配侥幸没错（next_hint 初始是 0，0 的 8 倍还是 0），第二次开始就全乱了。修正就是注释里那行：

let mut i = (a.next_hint / 8) as usize;   // 页号 ÷ 8 = 字节下标

两条教训，以后一直有用：

  1. 位图类代码里有三种数在流动：页号（第几页）、字节下标（位图第几字节）、位下标（字节内第几位）。每处换算都要问自己"我现在拿的是哪一种、要变成哪一种"
  2. 实验前先写预测数字。5000 6000 7000 是按机制一步步推出来的——预测写在前面，错了一目了然；没有预测，28000 这种数字看起来"也挺像个地址"，根本察觉不出错

本篇小结

  • alloc_frame：字节级粗扫 + 位级细查（trailing_zeros），返回物理地址，游标跟上
  • free_frame：置回 1，游标按需回退
  • 三段实验分别验证：分配顺序、页真的可写（魔数写读）、free 真的生效（收回重发拿回同一页）
  • 踩坑：页号/字节下标 8 倍混淆——三种数要分清，预测要先行
