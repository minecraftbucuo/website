03 · 串口输出：让内核开口说话

上一章：02-第一个内核。内核能编译了，但它是个
哑巴——跑没跑、卡在哪、死没死，外面一无所知。这一章给它装上
第一张"嘴"。

这一章要做成什么

一句话：让内核往串口打字，QEMU 的终端上能看到内核说的话。

要动两个文件：

  • 新建 kernel/src/serial.rs——串口驱动，约 90 行
  • 修改 kernel/src/main.rs——加一行模块声明，kmain 里打两句话

先打个预防针：本章写完、编译通过之后，还看不到字。因为内核还是
没人加载的"裸文件"（Limine 还没接上），打印的代码根本没机会执行。
本章的验证标准是编译干净通过；看到字要等下一章第一次开机。之所以
先写它，是因为它是内核的第一件"器官"，而且等 Limine 接上后立刻
就能用。

先理清楚：谁在干什么

先看我们要打通的输出链条，一共三站：

内核（往一个特殊地址写字节）
   → UART 芯片（主板上管串口的小芯片，把字节一位一位发出去）
      → QEMU（模拟器捕获这些字节，直接显示在你的终端上）

最后一站解释了为什么开发期串口这么好用：不用接任何线，QEMU 一条
参数就能把串口内容打到终端。将来真机上，这根线就是内核的"黑匣子"——
屏幕黑了，串口日志往往是唯一能告诉你死在哪的线索。

第一站有个必须想通的问题：println! 能用吗？不能——它是标准库的，
标准库依赖操作系统管屏幕，而我们就是在写操作系统。所以"让内核说话"
意味着直接跟硬件打交道。跟哪块硬件？整机里最简单的一块：串口。
屏幕当然也行，但屏幕要自己画像素、画字体，是好几章的工程；串口
几十行代码就通，先用最短路径让内核"能说话"，再说"说得好看"。

原理一：串口和 UART 芯片

串口的背后是一块叫 UART 的芯片（具体型号 16550），管着第一个
串口 COM1——就是老电脑背后那个梯形的 9 针接口。它的工作模式
像一位老实的老式电报员：你递给它一个字节，它就把这个字节一位一位
拍发出去，对面收到的还是这个字节。它在今天 PC 上的主业，就是给
内核当调试输出。

原理二：CPU 怎么跟它说话——两套地址空间

x86 有个乍听很怪的设计：CPU 有两套地址空间。把电脑想象成一个大
商场：

  • 内存地址空间像"店铺地址"——RAM、显存住在这里，用普通 mov
    指令读写；
  • IO 端口空间像"服务窗口编号"——老式外设在窗口后面办公，必须用
    专门的 in/out 指令，报上窗口号才能办事。
内存地址空间IO 端口空间
访问指令mov（普通读写）in / out（专用指令）
常住者RAM、显存UART、定时器、PS/2 键盘控制器等
容量按位数定（64 位）只有 65536 个端口

UART 的窗口号是 0x3F8。所以"往串口写一个字节"翻译成硬件动作
就是：执行 out 指令，端口 0x3F8，带上那个字节。

这套"窗口办公"是老式外设的接法。现代设备（NVMe 硬盘、USB 控制器）
大多直接住进内存空间，用普通 mov 访问。两种我们都会遇到，
先拿下简单的。

原理三：UART 的旋钮——寄存器

UART 不是只有一个窗口，而是从 0x3F8 起连着 8 个端口，各管一摊。
常用的就 4 个：

偏移名字用途
+0数据口写它 = 发一个字节；读它 = 收一个字节
+1中断使能本章全部关掉（0x00），中断是后面章节的事
+3线路控制设数据格式，还藏着一个开关位 DLAB（见下）
+5线路状态 (LSR)bit 5 = 空闲灯：亮着（=1）才能发下一个字节

为什么要看"空闲灯"？UART 拍发有物理速度（每秒几千位），你递字节的
速度超过它拍发的速度，多出来的就丢了。所以每次发之前先瞄一眼灯——
它是这章代码里唯一的"循环等待"。

初始化时还有两件事要办：

  • 波特率：双方约好的拍发速度。约不一致就是乱码——一个机关枪
    一个慢半拍。我们用 38400，它由一个"除数"决定（除数 3）。
  • DLAB 开关：UART 的面板按钮不够用，0 号和 1 号端口被做成了
    "双面按钮"——平时是数据口和中断使能，把 DLAB 拨到 1，它们翻面
    变成"波特率除数"，设完再拨回 0。年代久远的省成本设计，认识了
    就不觉得怪。

最后还有 Rust 这关：out/in 是内联汇编，必然是 unsafe。想象
编译器是一位非常负责的安检员，每件行李都亲眼看过才放行——但"往
0x3F8 窗口递东西"这件事，安检员根本看不见那个窗口，它无法证明
那儿真有 UART。Rust 的规则是：可以过，但要签字画押——签字栏
就叫 unsafe。它不是"危险代码垃圾场"，而是"编译器看不见、由程序员
担保"的声明。内核开发满地都是编译器看不见的硬件，unsafe 会一路
相伴；纪律是让每个 unsafe 块尽量小。

原理齐了，开始写代码。按依赖顺序分三步：先写最底层的"递字条"动作，
再包装成串口结构体，最后在 kmain 里说话。

动手一：outb / inb——最底层的递条动作

新建 kernel/src/serial.rs，先写两个端口读写原语：

use core::arch::asm;

/// 往 IO 端口写一个字节
pub fn outb(port: u16, value: u8) {
    unsafe {
        // out 指令的固定用法：端口地址放 dx，数据放 al
        asm!("out dx, al",
            in("dx") port,
            in("al") value,
            options(nomem, nostack, preserves_flags),
        );
    }
}

/// 从 IO 端口读一个字节（下一章收键盘数据时会用到）
pub fn inb(port: u16) -> u8 {
    let value: u8;
    unsafe {
        asm!("in al, dx",
            out("al") value,
            in("dx") port,
            options(nomem, nostack, preserves_flags),
        );
    }
    value
}

看 asm! 的写法：in("dx") port 表示"编译前把变量 port 装进 dx
寄存器"，out("al") value 表示"执行后把 al 寄存器倒回变量 value"。
options(...) 是写给安检员的说明书：这段汇编不碰内存、不碰栈、
不改标志位——你放心优化周围的代码。

注意两个函数的签名是安全的（pub fn 而不是 pub unsafe fn）：
危险被圈在函数体内部这一小块 unsafe 里，调用者不需要、也不应该
再写 unsafe。这就是"把 unsafe 圈到最小"的落地——unsafe 只应
出现在真正 unsafe 的地方。

动手二：SerialPort——把旋钮和窗口包成结构体

继续在 serial.rs 里加。初始化把所有旋钮拧到正确位置：

/// 一个串口。base 是它的端口基址（COM1 = 0x3F8）
pub struct SerialPort {
    base: u16,
}

impl SerialPort {
    /// COM1 的标准端口号，IBM PC 时代传下来的老门牌
    pub const COM1: u16 = 0x3F8;

    pub fn new(base: u16) -> Self {
        Self { base }
    }

    /// 开机时把旋钮拧到位：关中断 → 约速度 → 定格式 → 开缓冲
    pub fn init(&mut self) {
        outb(self.base + 1, 0x00); // 关串口中断（先静音）
        outb(self.base + 3, 0x80); // DLAB 拨到 1：0/1 号端口翻面成"波特率除数"
        outb(self.base + 0, 0x03); // 除数低字节 = 3 → 38400 波特
        outb(self.base + 1, 0x00); // 除数高字节
        outb(self.base + 3, 0x03); // DLAB 拨回 0；8 数据位、无校验、1 停止位
        outb(self.base + 2, 0xC7); // 开 FIFO 缓冲并清空
        outb(self.base + 4, 0x0B); // 数据终端就绪 + 请求发送
    }

七行 outb 对应原理三里说的每一件初始化事项，注释一一对应——
对着上面那张旋钮表读一遍就懂。注意 init 里没有 unsafe 块：
危险已经封在 outb/inb 最底层，上层代码保持干净。

然后是发送：

    /// 发一个字节。发之前先看 LSR 的空闲灯（bit 5）
    fn send_raw(&mut self, data: u8) {
        // 空闲灯没亮就一直看
        while inb(self.base + 5) & 0x20 == 0 {}
        outb(self.base, data);
    }

    /// 发送字符串。'\n' 自动补 '\r'
    pub fn send_str(&mut self, s: &str) {
        for &b in s.as_bytes() {
            match b {
                b'\n' => {
                    self.send_raw(b'\r');
                    self.send_raw(b'\n');
                }
                _ => self.send_raw(b),
            }
        }
    }
}

send_raw 里那个空循环叫忙等待：反复读状态位直到灯亮。效率
不高但简单可靠，裸机开发的基本功，等有了中断再升级。

send_str 里 \n 为什么要补 \r？电传打字机时代的化石：\r
（回车）= 打印头滑回行首，\n（换行）= 纸往上卷一行。只发 \n，
一些串口终端会把字打成"楼梯"——每行比上一行右移一格。

动手三：kmain——开口说话

最后改 kernel/src/main.rs，两处：

mod serial;   // 声明新模块（加在 use 之后）
#[unsafe(no_mangle)]
pub extern "C" fn kmain() -> ! {
    let mut com1 = serial::SerialPort::new(serial::SerialPort::COM1);
    com1.init();
    com1.send_str("\n=== MOS booting ===\n");
    com1.send_str("hello from kernel!\n");

    loop {
        core::hint::spin_loop();
    }
}

创建 COM1、初始化、说两句话——内核的"说话代码"就这么多。

验证：编译

cd ~/Desktop/MOS/kernel
cargo build

期待：零警告零错误。这就是本章的里程碑——打印代码已经就位，
等下一章 Limine 把它请上场，字就会出现在终端里。

踩坑实录

unnecessary unsafe block 警告。 最初版本里，init 和
send_raw 的函数体也包了 unsafe 块，编译器立刻警告。原因很值得
体会：outb/inb 用安全签名封装后，调用它们的代码里没有任何 unsafe
操作——包着的全是安全函数，编译器说"这里没有危险，你签什么字"。
修法就是上面看到的：unsafe 只住在 outb/inb 两个函数体内部，想审查
危险代码只需要看这两个小块。

顺带一个反例：如果反过来写 pub unsafe fn 再在体内包 unsafe 块，
也会报同样的警告——unsafe fn 的函数体默认整块就是 unsafe 的，
重复签字会被编译器瞪。

本章小结

  • 输出链条：内核写端口 → UART 拍发 → QEMU 显示到终端；println!
    不能用，因为标准库依赖操作系统
  • x86 两套地址空间：内存（mov）和 IO 端口（in/out）；COM1
    的窗口号 0x3F8
  • UART 四个关键旋钮：数据口、中断使能、线路控制（DLAB 开关）、
    线路状态（空闲灯）
  • unsafe 的纪律：圈到最小，只住在最底层，签名保持安全

里程碑：串口驱动编译通过，内核具备了"说话"的能力 ✅
