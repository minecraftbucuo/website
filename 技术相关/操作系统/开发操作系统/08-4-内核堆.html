08 · 内存管理（四）：内核堆

上一篇：08-3-发页与收页。页帧分配器会发页了——但它的最小单位是 4KB。
想 Box::new(0u64) 存一个 8 字节的数？也得领一整页，剩下 4088 字节全浪费。
本篇在页之上建字节级分配器（内核堆），并接上 Rust 的 GlobalAlloc 接口，
让 Box、Vec 在内核里直接可用。

原理：为什么要有堆

页帧分配器的粒度是页：只能给 4KB 的整数倍。可内核日常要存的绝大多数东西远小于一页——一个进程控制块、一行日志缓冲、一个 Vec 的元素区。粒度差了三个数量级，直接用页就是灾难：存 100 个 8 字节对象要领 100 页（400KB），实际只用 800 字节。

解法是再加一层：先从页帧分配器领一批页，再在这批页内部做字节级的切分。这层就是内核堆（heap）。外面要 8 字节，堆在自己管理的内存里划出 8 字节给出去；外面不要了，堆把那 8 字节记回可用。

堆内部怎么记账？算法有很多（链表法、伙伴系统……），本篇用最简单的一种：bump 分配。

  • 堆的全部状态就是一个游标 top：已分配到哪了
  • 分配 len 字节：把游标对齐到要求，检查剩余空间够不够，够就把游标前移 len，返回原来的位置
  • 收回：什么都不做——游标只进不退，内存只出不进

分配快到极致（几次算术运算），代价是内存无法回收：堆用满的那一刻就再没有任何分配能成功。这个缺陷是故意的：v1 先跑通整条链路，堆的真正实现（能回收的）留给后面的章节。堆开大一点（1080 页 ≈ 4.2MB）——番外篇贪吃蛇的 4MB 双缓冲画布就是从这里拿的。

原理：GlobalAlloc——Rust 分配世界的接口

第二个问题：怎么让 Box::new(...) 自己找到我们的堆？

Box::new 的内部没有任何魔法：它要内存时调用的是 Rust 定义的全局分配接口——GlobalAlloc trait，就两个方法：

pub unsafe trait GlobalAlloc {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8;      // 给内存，失败返回空指针
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout); // 归还
}
  • Layout：一次请求的打包描述——要多少字节（size）、按几字节对齐（align）
  • 失败约定是返回空指针，不是 panic——调用方（Box/Vec）自己决定失败了怎么办

Rust 标准库其实分三层：core（永远有）、alloc（Box/Vec/String 等，需要有人提供 GlobalAlloc）、std（完整标准库，alloc 的超集）。我们 #![no_std] 意味着只有 core；只要在 main.rs 写 extern crate alloc; 并用 #[global_allocator] 指定一个实现了 GlobalAlloc 的类型，Box/Vec 就全通了——它们的所有分配自动走我们的堆。

最后是那个 unsafe impl：编译器无法审查分配器的实现（全是裸指针运算和约定），所以要求实现者显式写下"我担保"——担保内容：返回的指针对齐正确、不重叠、dealloc 收到的指针确实是 alloc 发出去的。担保不成立，上层代码全部 UB。

动手八：heap.rs

新建 kernel/src/heap.rs，main.rs 模块区加 mod heap;。整个文件分四块。

第 1 块：堆的状态——三个数：

//! 内核堆（第一版）：bump allocator。对应教程：docs/08-4-内核堆.md
//!
//! 页帧分配器（mm.rs）只按整页 4KB 分配；堆垫在它上面，
//! 按任意字节数分配、随时归还。
//!
//! bump 分配：游标只往上移，分配 = 游标前移。
//! 代价是 free 不回收内存——第一版的诚实缺陷，以后换真正的分配器。

use crate::mm;
use core::sync::atomic::{AtomicUsize, Ordering};

// 三个原子量 = 堆的全部状态。0 表示还没建堆
static START: AtomicUsize = AtomicUsize::new(0); // 堆底（虚拟地址）
static SIZE: AtomicUsize = AtomicUsize::new(0); // 总大小（字节）
static TOP: AtomicUsize = AtomicUsize::new(0); // 游标：已用到的偏移

START 记堆底的虚拟地址（堆内存经 HHDM 访问，TOP 是相对堆底的偏移）。还是 AtomicUsize 替代 static mut 的老配方。

第 2 块：建堆——从页帧分配器领页：

/// 建堆：向页帧分配器要一段连续的 pages 页。
/// 返回 false = 找不到这么长的连续空闲段
///（bump 堆靠 HHDM 直映射用内存，物理连续才在虚拟地址上连成一块）
pub fn init(pages: u64) -> bool {
    let first = match mm::alloc_frame_contig(pages) {
        Some(p) => p,
        None => return false,
    };

    START.store(mm::phys_to_virt(first) as usize, Ordering::Relaxed);
    SIZE.store((pages * mm::PAGE_SIZE) as usize, Ordering::Relaxed);
    TOP.store(0, Ordering::Relaxed);
    true
}

关键点是连续：堆要把这些页当一整块连续内存用。可内存清单上的 usable 区段有长有短、彼此不挨着——逐页领的话，领到区段边界就会撞上不连续。所以 mm.rs 提供专门的 alloc_frame_contig(pages)：线性扫一遍位图，数"连续空闲"串的长度，够长就整段标成已占、返回起点。找不到就老实宣布失败。

第 3 块：分配与收回：

/// 分配 len 字节、按 align 对齐。堆满返回 None
///
/// 注：load/store 不是原子读改写，这里默认"单核、且中断处理函数
/// 不碰堆"；真正要并发安全时（多核），这里得换成 CAS 循环
pub fn alloc(len: usize, align: usize) -> Option<*mut u8> {
    let start = START.load(Ordering::Relaxed);
    if start == 0 {
        return None; // 堆还没建
    }
    let size = SIZE.load(Ordering::Relaxed);
    let mut top = TOP.load(Ordering::Relaxed);

    // 对齐：游标不够齐就垫高到 align 的倍数（垫的缝隙浪费掉，不记账）
    top = (top + align - 1) & !(align - 1);
    if top + len > size {
        return None; // 堆满。bump 堆不回收，满 = 完
    }
    TOP.store(top + len, Ordering::Relaxed);
    Some((start + top) as *mut u8)
}

/// 归还。bump 版：什么都不做
pub fn dealloc(_ptr: *mut u8) {}

对齐那一行值得单独讲。对齐公式：

(x + n - 1) & !(n - 1)   =  把 x 向上取整到 n 的倍数（n 是 2 的幂）

代入数字感受一下：x = 13, n = 8 → (13 + 7) & !7 = 20 & 0b...11111000 = 16——13 被垫到 16。原理：n - 1 的二进制是低 k 位全 1（8 = 0b1000，7 = 0b111），!(n-1) 把低 k 位清零 = 抹掉不足一整份的零头；先加 n-1 保证"只要 x 不是整数倍就进位到下一个倍数"。上一章 and rsp, -16（栈对齐）干的是同一件事——负数按补码正好是 !(n-1) 的形式。

这个公式为什么成立还有一个角度：n 是 2 的幂时，"n 的倍数"就是"二进制低 k 位全是 0 的数"——位运算清零是最直接的表达。

第 4 块：接上 GlobalAlloc：

// ---------- 接入 Rust 分配世界 ----------
// Box/Vec 不自己分配，全走 GlobalAlloc 这扇门；
// 我们把门后的活指给上面的 bump 堆

use core::alloc::{GlobalAlloc, Layout};

/// 挂在 #[global_allocator] 上的零大小标记类型
struct KernelHeap;

// unsafe：编译器对这里的实现零审查、全盘信任——
// 返回的指针不对齐/重叠，上层 UB，全是我们兜
unsafe impl GlobalAlloc for KernelHeap {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        // 协议翻译：trait 要"失败 = 空指针"，我们的堆说 Option
        match alloc(layout.size(), layout.align()) {
            Some(ptr) => ptr,
            None => core::ptr::null_mut(),
        }
    }

    unsafe fn dealloc(&self, ptr: *mut u8, _layout: Layout) {
        dealloc(ptr);
    }
}

#[global_allocator]
static ALLOCATOR: KernelHeap = KernelHeap;

KernelHeap 是个零大小类型——它没有任何数据，纯粹是"实现挂在哪"的标记，真正的状态在上面三个 static 里。它做的事只有协议翻译：我们的堆说"失败 = None"，trait 说"失败 = 空指针"，中间翻译一下。最后 #[global_allocator] 声明"全局分配接口由 KernelHeap 实现"——从此全内核的 Box/Vec 分配都走这条路。

动手九：接线与实验（main.rs）

开 alloc 之门：main.rs 顶部（#![no_std]/#![no_main] 之后）：

// alloc：标准库的"分配件"（Box/Vec 等）单独成库，no_std 也能用，
// 前提是有人提供 GlobalAlloc——heap.rs 干的就是这个
extern crate alloc;

没有这行，Box/Vec 在 no_std 内核里根本不存在（编译报错找不到）。

实验代码：在 free 2nd frame 实验之后、同一个分支内：

                    // 建堆：1080 页（约 4.2MB）——
                    // 番外篇贪吃蛇的 4MB 双缓冲画布是堆的头号大客户
                    if heap::init(1080) {
                        serial::print("heap up: ");
                        serial::print_hex(1080);
                        serial::print(" pages\n");

                        // 内核里第一次动态分配
                        let b = alloc::boxed::Box::new(0x1234_5678u64);
                        let mut v = alloc::vec::Vec::new();
                        for i in 0..5u64 {
                            v.push(i * 111);
                        }
                        serial::print("box = ");
                        serial::print_hex(*b);
                        serial::print(", vec len = ");
                        serial::print_hex(v.len() as u64);
                        serial::print(", vec[4] = ");
                        serial::print_hex(v[4]);
                        serial::print("\n");
                        // 作用域结束：Drop 自动调 dealloc（bump 堆不回收，没有实际效果）
                    } else {
                        serial::print("heap init failed!\n");
                    }

Box::new(0x1234_5678u64) 干了什么？向 GlobalAlloc::alloc 请求 8 字节、8 对齐 → heap::alloc → bump 游标前移 8 → 把值写进去。编译时完全不知道堆的实现——它只认 GlobalAlloc 这个接口。

Vec 更有意思：Vec::new() 不分配任何内存（容量为 0）；第一次 push 时才申请能放 4 个 u64 的空间（32 字节）；push 到第 5 个，32 字节装不下了，Vec 再申请一块更大的、把旧数据搬过去、把旧块还回来（bump 堆对"还回来"没有实际动作）。这一串操作全部自动经过 GlobalAlloc → 我们的堆。

运行验证

make run

串口在 realloc got: 6000 之后应多出两行：

heap up: 438 pages
box = 12345678, vec len = 5, vec[4] = 1BC

438 是十六进制（print_hex 不带 0x 前缀），= 十进制 1080 页。

对照验算：

  • box = 12345678：存进去的 0x1234_5678 原样读出来了——Box 经 GlobalAlloc → heap::alloc → mm::alloc_frame 拿到的内存真实可用，分配链路三层全通
  • vec len = 5、vec[4] = 1BC：push 了 5 个值，4 × 111 = 444，十六进制 0x1BC——包括那次"扩容搬家"在内的 6 次分配全部正确

这两行打出来，标志着 Box、Vec、以及一切依赖动态分配的 Rust 数据结构在内核里解锁。以后写内核代码，就跟写普通 Rust 程序一样用它们了。

失败情况：heap init failed! = 领不到 16 连页；开机卡在半路（串口没下文）= 分配失败返回空指针后 Box 内部 panic——panic_handler 现在只是死循环，表现为"卡住"，这也提醒我们 panic 处理该升级了（顺理成章的事，现在能分配内存了）。

本篇小结

  • 堆 = 页之上的字节级分配器；bump 版全部状态是三个数，分配 = 对齐 + 前移游标
  • 对齐公式 (x + n - 1) & !(n - 1)：向上取整到 2 的幂的倍数
  • extern crate alloc + #[global_allocator]：Box/Vec 的分配自动接入我们的堆，内核从此能用动态数据结构
  • bump 的代价：free 不回收，堆用满即终——换真分配器是后面的章节
