04 · 第一次开机：Limine、ISO 与 QEMU

上一章：03-串口输出。内核会说话了，但它还躺在
文件里——从来没有人把它加载进内存、执行过。这一章接通最后一环。

这一章要做成什么

一句话：做出一个可启动的 mos.iso，在 QEMU 里第一次开机，亲眼看到
串口终端打出 hello from kernel!——前面两章写的所有代码，在这一刻
第一次真正运行。

要动的东西：

  • 新建 limine.conf——告诉 Limine 去哪找内核
  • 新建 Makefile——把"编译 → 打包 → 开机"固化成三条命令
  • 新建 kernel/build.rs——3 行，解决一个 cargo 的跟踪盲区
  • 修改 kernel/linker.ld——修一个 Limine 拒绝加载的问题（见踩坑实录）
  • 下载 limine/ 目录——Limine 引导器本体，make limine 一条命令搞定，
    不进 git

先理清楚：为什么需要这三个新东西

回忆第 00 章的分工：UEFI 固件负责开机第一棒。但它有条死规矩——
只认 EFI 应用（UEFI 规范定义的一种程序格式）。我们的内核是
裸机 ELF，UEFI 看都不看它一眼。

所以第 00 章说过，需要请一位"有资格被 UEFI 加载"的帮手进场：
Limine 引导器。它本身就是一个 EFI 应用，UEFI 愿意加载它；
它被加载后替我们干完脏活（切 64 位、建页表、设置屏幕），把我们的
内核 ELF 摆进内存、跳进去。它还有个决定性优点：同一个镜像，BIOS
老机器和 UEFI 新机器都能启动——真机兼容性直接拉满。

第二个问题是"怎么打包"。内核、Limine、配置文件是三个散装文件，
得按某种格式组装成一个整体。用 ISO——光盘的文件系统格式。
打包产物 mos.iso 有三种身份：磁盘上的一个普通文件、QEMU 里的
虚拟光盘、dd 到 U 盘后就是启动盘。

第三个问题在 QEMU 这边：QEMU 默认模拟的是 90 年代的老式 BIOS 机器，
而我们的目标是 UEFI。给 QEMU 换上 UEFI 的"固件"就行——OVMF，
UEFI 固件的开源实现，两个文件：OVMF_CODE.4m.fd（固件本体，只读）
和 OVMF_VARS.4m.fd（可写的设置存储，相当于真机主板 CMOS 里那块
存 BIOS 设置的区域）。

三者备齐，链条是：OVMF（扮演 UEFI）→ 放行 Limine → Limine 按配置
加载我们的内核 → 内核运行、串口打字。

动手一：下载 Limine

Limine 是编译好的发布包，下载解压即可。我们把它固化成 Makefile
里的一个目标，你在项目根目录执行：

make limine

它做三件事：从 GitHub 下载 limine-binary.zip（约 2MB，国内网络
慢属正常）→ 解压到 limine/ 目录（--strip-components=1 是因为
压缩包里套了一层目录，不剥掉的话 Makefile 会找不到文件——见
踩坑实录）→ 编译它的一个宿主小工具 limine（后面打包要用）。

完成后 limine/ 里有几个文件值得认识：

文件干什么用
limine-bios.sys / limine-bios-cd.binBIOS 模式的引导数据
limine-uefi-cd.binUEFI 模式的引导数据
BOOTX64.EFIUEFI 固件寻找的启动文件（就是 Limine 本体）
limine（刚编译出的）宿主工具，负责往 ISO 里安装 BIOS 引导记录

动手二：limine.conf——启动配置

Limine 加载内核之前得知道：启动项叫什么、用什么协议、内核文件在哪。
这些写进项目根目录的 limine.conf：

# 菜单等待秒数，0 = 不显示菜单直接进第一项
timeout: 0

# 启动项：MOS
/MOS
    # 使用 Limine Boot Protocol（我们的内核就是按这个协议写的）
    protocol: limine

    # 内核路径。boot(): = 本配置文件所在的卷（也就是 ISO 根）
    kernel_path: boot():/mos-kernel

这是 Limine v8+ 的新语法（启动项以 / 开头，键值用冒号）。读法：
启动项叫 "MOS"，用 Limine 协议，加载 ISO 根目录下名为 mos-kernel
的文件——那个名字就是我们编译产物的"装箱名"。

动手三：Makefile——把流程固化

到目前为止每章都是散装命令。从这章开始流程变长（编译 → 装箱 →
安装引导记录 → 开机），必须固化。新建项目根目录的 Makefile：

KERNEL_ELF := kernel/target/x86_64-unknown-none/debug/mos-kernel
LIMINE_DIR := limine
OVMF_CODE  := /usr/share/ovmf/x64/OVMF_CODE.4m.fd
OVMF_VARS  := OVMF_VARS.4m.fd

开头是四个路径变量：内核产物、Limine 目录、OVMF 两件套。

iso: $(KERNEL_ELF)
	mkdir -p iso_root/EFI/BOOT
	cp $(KERNEL_ELF) iso_root/mos-kernel
	cp limine.conf iso_root/
	cp $(LIMINE_DIR)/limine-bios.sys $(LIMINE_DIR)/limine-bios-cd.bin \
	   $(LIMINE_DIR)/limine-uefi-cd.bin iso_root/
	cp $(LIMINE_DIR)/BOOTX64.EFI iso_root/EFI/BOOT/
	xorriso -as mkisofs -R -r -J \
	    -b limine-bios-cd.bin -no-emul-boot -boot-load-size 4 -boot-info-table \
	    --efi-boot limine-uefi-cd.bin -efi-boot-part --efi-boot-image \
	    --protective-msdos-label \
	    iso_root -o mos.iso
	$(LIMINE_DIR)/limine bios-install mos.iso

make iso 做两阶段的事。前五条 cp/mkdir 把所有材料汇进
iso_root/ 这个"待打包目录"——注意 EFI/BOOT/BOOTX64.EFI 这个
路径是 UEFI 规范写死的默认启动路径，固件开机时挨个设备找它，
找到就执行；U 盘"插上就能进启动菜单"靠的就是这条规矩。然后
xorriso 把目录打成 ISO：那一长串参数的本质是往镜像里同时缝
两条引导记录（-b 一条 BIOS 用的、--efi-boot 一条 UEFI 用的），
这就是"双模式启动"的物理实现。最后 limine bios-install 给 BIOS
那条记录补上安装仪式（写引导扇区信息）。

run: iso
	@test -f $(OVMF_VARS) || cp /usr/share/ovmf/x64/OVMF_VARS.4m.fd $(OVMF_VARS)
	qemu-system-x86_64 -M q35 -m 512M \
	    -drive if=pflash,format=raw,readonly=on,file=$(OVMF_CODE) \
	    -drive if=pflash,format=raw,file=$(OVMF_VARS) \
	    -cdrom mos.iso \
	    -serial stdio \
	    -no-reboot -no-shutdown

make run 先确保 OVMF 的"设置存储"在项目里有一份可写副本（固件
要求 VARS 可写，/usr/share 下那份是只读的，所以第一次运行前
拷一份），然后启动 QEMU。参数表：

参数含义
-M q35机器型号（较新的芯片组，接近现代真机）
-m 512M内存 512 MB
-drive if=pflash,...挂载 OVMF 固件（CODE 只读 + VARS 可写）
-cdrom mos.iso把我们的"光盘"插进光驱
-serial stdio串口接到当前终端——内核的话直接打在你眼前
-no-reboot出错时不自动重启（裸机出错常表现为反复重启，调试时先摁住）

最后补两个辅助目标（完整文件见仓库 Makefile，还有 check 只编译、
burn 刻 U 盘、clean 清理）。

一个伏笔：Makefile 里 iso 依赖 $(KERNEL_ELF)，改动内核后
make run 会自动重编——但 cargo 有个盲区：它不跟踪 linker.ld
的变化（链接脚本不在它的依赖清单里）。下一段动手就修它。

动手四：build.rs——让 cargo 盯住链接脚本

新建 kernel/build.rs：

fn main() {
    println!("cargo:rerun-if-changed=linker.ld");
}

build.rs 是 cargo 的构建脚本机制：编译 crate 前先运行它。
rerun-if-changed 声明"linker.ld 也算源文件，它变了请重新链接"。
就 3 行，但少了它你会遇到"改了链接脚本、重编了、行为没变"的灵异
现象——因为 cargo 看了看 .rs 文件说"没变化"，直接跳过。

开机：make run

万事俱备，项目根目录执行：

make run

终端会滚动一段 OVMF 的启动日志（BdsDxe: loading Boot0002 ... 是
UEFI 固件在扫描启动设备、找到我们的虚拟光盘），然后你等待已久的两行：

=== MOS booting ===
hello from kernel!

这是内核说的话：Limine 把内核摆进内存、建好页表、跳进 _start，
我们的汇编立起栈，call kmain 进入 Rust，串口旋钮拧到位，字节穿过
模拟的 UART 芯片回到了你的终端。前两章写的代码，第一次真正运行。

退出 QEMU 的组合键：先按 Ctrl+A，松开再按 X。串口被 QEMU 占用
着，Ctrl+C 退不出去——这个组合键很快会变成肌肉记忆。

踩坑实录

坑 1：elf: Attempted to load ELF file with PHDRS with different permissions sharing the same memory page.（Limine 拒绝加载）

第一次开机时遇到的。用 readelf -lW 内核文件 检查发现：只读的
.rodata 段结束在 0x...1114，而可写的 .got（全局偏移表，16 字节）
在 0x...1118——权限不同的两段挤进了同一个内存页。页是权限的
最小单位，Limine 无法向 CPU 声明"这页能写还是不能写"，直接拒绝加载。

根源是个隐蔽的链接器行为：我们的脚本只点名了 .text/.rodata/.data/.bss
四个节，编译器额外产出的 .got 成了"孤儿节"，链接器随手把它塞进
上一个节后面、不做页对齐。修法是在 linker.ld 的 .data（可写区）
里把常见孤儿节显式收编：

.data : ALIGN(4K) {
    *(.data .data.*)
    *(.data.rel.ro .data.rel.ro.*)
    *(.got .got.*)
    *(.init_array .init_array.*)
    *(.fini_array .fini_array.*)
}

修完用 readelf -lW 复查：可写段独占新页 0x...12000，与只读段
再无瓜葛，Limine 放行。

坑 2：make: *** 没有指明目标并且找不到 makefile。

make limine 首次运行报的错。ls limine/ 一看：里面只有一个
limine-binary/ 子目录——压缩包里套了一层目录，所有文件
（包括 Makefile）被解进了子目录。修法：解压命令加
--strip-components=1 剥掉外层目录。经验：解压完 ls 一眼，
确认文件在预期的位置。

上真机（阶段性验证）

每个里程碑，可以把同一个镜像放上真机：

# 危险操作：sdX 必须是 U 盘，dd 没有撤销键，写错盘 = 数据全没
lsblk                  # 先确认 U 盘设备名
sudo dd if=mos.iso of=/dev/sdX bs=4M status=progress oflag=direct
sync

然后目标机：插 U 盘 → 开机按 F12 进启动菜单 → 选 U 盘。两个注意
事项：UEFI 设置里要关闭 Secure Boot（Limine 未做签名，固件
验签不过不放行）；想看串口日志需要一根 USB 转串口线，没有的话
等下一章做好屏幕显示再上真机。

本章小结

  • UEFI 只认 EFI 应用，所以需要 Limine 当"被放行的加载者"；ISO 把
    内核 + Limine + 配置打包成 U 盘/光驱通吃的镜像；OVMF 让 QEMU
    模拟 UEFI 机器
  • EFI/BOOT/BOOTX64.EFI 是规范写死的默认启动路径
  • 孤儿节会破坏页权限隔离，要么在链接脚本里显式收编，要么等着
    Limine 拒载
  • cargo 不跟踪链接脚本，build.rs 一行声明补上盲区
