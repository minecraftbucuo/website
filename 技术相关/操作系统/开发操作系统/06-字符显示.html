06 · 字符显示：给内核装一台打字机

上一章：05-帧缓冲显示。内核能往屏幕上画像素了，
但想在屏幕上"说话"，总不能每个字都手算像素——这一章把像素升级成文字。

这一章要做成什么

一句话：给内核装一台"打字机"——调用 write_str，屏幕上就滚出一行行字符。

上一章内核拿到了显存、会画单个像素，但 "hello" 是 5 个字节，从字节到"看起来像 h 的图案"中间还缺一层东西。补上这一层，就是本章的全部工作。

要动的东西：

  • 新建 tools/gen_font.py——字体提取脚本，从 Linux 自带的控制台字体里抠点阵
  • 生成 kernel/src/font.rs——字模表（脚本产物，但作为源码进 git，见后文）
  • 新建 kernel/src/console.rs——文本控制台：画字符、管光标、滚屏
  • 修改 kernel/src/main.rs——接线，开机打字
  • 修改 Makefile——补上一条"内核从哪来"的规则（这次踩到了全项目最阴的坑）

全部就位后 make run，屏幕从上一章的渐变图变成满屏文字。

原理：字模——每个字符一张点阵图纸

先回答开头那个"中间缺的一层"是什么：每个字符长什么样的图纸。

屏幕上的一个字符，其实就是一小块像素方格里亮、暗点的固定图案。以字母 A 为例（# 代表亮像素）：

........
...#....
...#....
..#.#...
..#.#...
.#...#..
.#####..
.#...#..
.#...#..
........
（下面几行空着，共 16 行）

这种图纸叫字模。它的存储方式非常省：一行 8 个点正好打包成 1 个字节（每位一个点，1 = 亮），16 行就是 16 字节一个字符。可打印的 ASCII 共 96 个（空格 0x20 到 ~ 0x7E），全部塞进一张表也才 1536 字节——不到 1.5KB，直接嵌进内核当查询表：要画字符 c，就取表里第 c 项的 16 个字节，逐位翻译成屏幕像素。

图纸有了，还得有人往屏幕上"盖"。所以本章的分工是：

font.rs     印章库：字符 → 16 字节点阵图纸（只管存）
console.rs  打字机：拿图纸往显存盖章、记住光标在哪、管换行和滚屏（管动）
main.rs     接线：开机时初始化打字机，之后随便打字

剩下一个问题：图纸数据从哪来？96 个字符手敲不现实（也必然敲错）。答案是现成的——你的 Linux 机器上就有。

印章从哪来：Linux 自带的位图字体

还记得 Ctrl+Alt+F2 切出的那个黑屏文字终端吗？它不靠图形库，用的正是位图字体，文件躺在 /usr/share/kbd/consolefonts/ 下，标准格式叫 PSF。我们选 cp850-8x16.psfu.gz：8×16 正好是我们要的尺寸；cp850 是 DOS 时代代码页，前 128 个字符位与 ASCII 完全一致（高半区还有画框线的制表符，将来也许用得上）。

PSF 文件的结构简单得出奇，一共三段：

┌──────────────┐
│ 文件头        │ PSF1：4 字节；PSF2：32 字节（魔数 + 一组字段）
├──────────────┤
│ 字形数据      │ 256 个字形连续平铺，每个 16 字节——就是我们要的
├──────────────┤
│ Unicode 映射表│ 声明每个字形对应哪些字符（文件名里的 u 指它），用不到
└──────────────┘

文件头第一样东西是魔数（magic）：开头几个固定字节，格式的"接头暗号"——和 Limine 请求开头那 16 字节魔数是一个思路。PSF1 用 36 04，PSF2 用 72 B5 4A 86，认出版本才知道头有多长、从哪开始切字形。

至于字形数据：每字节一行、每字节 8 个像素、最高位对应最左边的像素。整个文件里最值钱的 4096 字节就是中间那段。

动手一：gen_font.py——把字形数据抄出来

提取脚本是一次性工具，放 tools/gen_font.py（进 git，换字体可重跑）。分两段看。

第一段：解压、认格式、切出字形数据：

#!/usr/bin/env python3
"""从 Linux 控制台字体提取点阵，生成 kernel/src/font.rs"""
import gzip
import struct
import sys

FONT = "/usr/share/kbd/consolefonts/cp850-8x16.psfu.gz"
OUT = "kernel/src/font.rs"

with gzip.open(FONT, "rb") as f:
    data = f.read()

# 认格式：看魔数（PSF2: 72 B5 4A 86，PSF1: 36 04）
if data[:4] == b"\x72\xb5\x4a\x86":  # PSF2
    (version, headersize, flags,
     length, charsize, height, width) = struct.unpack("<7I", data[4:32])
    assert width == 8, "不是 8 像素宽的字体"
elif data[:2] == b"\x36\x04":  # PSF1
    mode, charsize = data[2], data[3]
    headersize = 4
else:
    sys.exit("不认识的字体格式")

# 切出前 256 个字形，每个 charsize 字节
glyphs = data[headersize:headersize + 256 * charsize]
assert len(glyphs) == 256 * charsize, "字形数量不足 256"

struct.unpack("<7I", ...) 按"小端、7 个 u32"解包 PSF2 头部（< = 小端，x86 本身就是小端；I = u32）。两个版本头长不同，认出版本后从对应位置开始切。两个 assert 确保字体真是 8 宽、真有 256 个字形——提取脚本最怕"静默提取了半截"。

第二段：排成 Rust 源码：

# 排成 Rust 源码
lines = [
    "//! 字模表：由 tools/gen_font.py 从 cp850-8x16.psfu.gz 生成，勿手改",
    "//! 每字符 16 行 × 1 字节/行（8 像素），最高位 = 最左像素",
    "",
    "pub const GLYPH_WIDTH: usize = 8;",
    "pub const GLYPH_HEIGHT: usize = 16;",
    "",
    "pub const GLYPHS: [[u8; GLYPH_HEIGHT]; 256] = [",
]
for i in range(256):
    rows = glyphs[i * charsize:(i + 1) * charsize]
    hexes = ", ".join(f"0x{b:02X}" for b in rows)
    label = chr(i) if 32 <= i < 127 else ""  # 可打印字符在行尾标注
    lines.append(f"    [{hexes}], // 0x{i:02X} {label}")
lines += ["];", ""]

with open(OUT, "w") as f:
    f.write("\n".join(lines))
print(f"OK: {OUT}（{256 * charsize} 字节字模数据）")

生成的 font.rs 长这样（节选）：

pub const GLYPHS: [[u8; GLYPH_HEIGHT]; 256] = [
    // ...0x40 之前略...
    [0x00, 0x00, 0x10, 0x38, 0x6C, 0xC6, 0xC6, 0xFE, 0xC6, 0xC6, 0xC6, 0xC6, 0x00, 0x00, 0x00, 0x00], // 0x41 A
    [0x00, 0x00, 0xFC, 0x66, 0x66, 0x66, 0x7C, 0x66, 0x66, 0x66, 0x66, 0xFC, 0x00, 0x00, 0x00, 0x00], // 0x42 B
    // ...
];

设计上一个决定值得说明：存满 256 个字形、用字符编码直接当下标（GLYPHS[b'A' as usize]），而不是只存 96 个再算偏移。多花 1.5KB 换来"零换算、数组下标天然带边界检查"，值。

生成命令（项目根目录）：

python tools/gen_font.py

预期输出 OK: kernel/src/font.rs（4096 字节字模数据）。想亲眼验货，看一眼 A 的图纸：

grep '0x41 ' kernel/src/font.rs

对着本节开头的点阵图读那 16 个字节：0x10 = 00010000，正是 A 顶部的单点。

顺带一个约定：font.rs 虽是生成物，但进 git——不然每台编译机都得装 kbd 包才能构建，得不偿失。它 4KB 的体积代价可以忽略。

动手二：console.rs——打字机本体

图纸备齐，现在造打字机。先把它的世界观说清楚：在像素之上叠一层字符网格——屏幕宽 1024 像素、字模宽 8 像素，一行能放 128 个字符；高 768、字模高 16，能放 48 行。光标就是"下一个字落在哪个格子"，记一个列号、一个行号而已。

打字机要会三个动作：盖章（拿图纸把一个格子涂满）、走纸（光标右移、行满换行）、滚屏（打满一屏时整屏上移一行）。一个要先想清楚的问题：盖章时只画亮点、不画暗点行不行？不行——光标格子可能残留着上一章的旧图案，只画亮点新字会叠在旧图上。所以每个 8×16 格子整个涂满：亮位写前景色、暗位写背景色，旧像素被完整覆盖，连"擦除"这步都省了。

分四段写 kernel/src/console.rs。

第一段：结构体与初始化——记住屏幕参数，算出网格，光标归零：

use crate::boot::Framebuffer;
use crate::font::{GLYPH_HEIGHT, GLYPHS, GLYPH_WIDTH};

/// 文本控制台：屏幕参数 + 光标位置
pub struct Console {
    base: *mut u8, // 显存起始地址
    width: usize,  // 屏幕宽（像素）
    height: usize, // 屏幕高（像素）
    pitch: usize,  // 行距：一行像素实际占的字节数
    cols: usize,   // 一行能放几个字符
    rows: usize,   // 一共几行字符
    col: usize,    // 光标：当前列
    row: usize,   // 光标：当前行
    fg: u32,       // 前景色（笔画颜色）
    bg: u32,       // 背景色
}

impl Console {
    /// 白字黑底。颜色排布是 0x00BBGGRR，同上一章渐变图的算法
    pub fn new(fb: &Framebuffer) -> Self {
        Self {
            base: fb.address(),
            width: fb.width as usize,
            height: fb.height as usize,
            pitch: fb.pitch as usize,
            cols: fb.width as usize / GLYPH_WIDTH,
            rows: fb.height as usize / GLYPH_HEIGHT,
            col: 0,
            row: 0,
            fg: 0x00FFFFFF,
            bg: 0x00000000,
        }
    }

屏幕参数是上一章从 Limine 手里拿的，原样抄进来。cols/rows 用整除算出——若屏幕高不是 16 的整数倍，最底剩的几行像素干脆闲置，无害。

第二段：盖章——全章最核心的 10 行，图纸到像素的翻译：

    /// 把字符 ch 盖进 (col, row) 格子：亮点位写前景色，暗点位写背景色
    fn draw_char(&self, col: usize, row: usize, ch: u8) {
        let glyph = &GLYPHS[ch as usize];
        let x0 = col * GLYPH_WIDTH; // 格子左上角的像素坐标
        let y0 = row * GLYPH_HEIGHT;

        for (dy, &bits) in glyph.iter().enumerate() {
            for dx in 0..GLYPH_WIDTH {
                // 0x80 >> dx：从最高位（最左像素）开始逐位检查
                let color = if bits & (0x80 >> dx) != 0 { self.fg } else { self.bg };
                unsafe {
                    let p = self.base.add((y0 + dy) * self.pitch + (x0 + dx) * 4) as *mut u32;
                    p.write_volatile(color);
                }
            }
        }
    }

外层循环走 16 行（dy），内层走 8 列（dx）；0x80 >> dx 依次生成 10000000、01000000……逐位探测图纸。写像素的地址公式和 unsafe 纪律与上一章完全一致——危险依然只圈在写显存的最底层。

第三段：清屏与滚屏——滚屏就是一次大搬运：

    /// 整屏涂成背景色
    pub fn clear(&mut self) {
        for y in 0..self.height {
            for x in 0..self.width {
                unsafe {
                    let p = self.base.add(y * self.pitch + x * 4) as *mut u32;
                    p.write_volatile(self.bg);
                }
            }
        }
    }

    /// 滚屏：整屏内容上移一行，最底一行腾出来
    fn scroll(&mut self) {
        let char_row = GLYPH_HEIGHT * self.pitch; // 一个字符行占的字节数
        unsafe {
            // ptr::copy 是 memmove 语义：源和目的重叠也能正确搬运
            core::ptr::copy(
                self.base.add(char_row),   // 源：第 1 行字符开头
                self.base,                  // 目的：第 0 行字符开头
                (self.rows - 1) * char_row, // 搬 (rows-1) 行的量
            );
        }
        self.clear_char_row(self.rows - 1); // 最底行涂黑
    }

    /// 把第 row 行字符格涂成背景色
    fn clear_char_row(&mut self, row: usize) {
        for y in row * GLYPH_HEIGHT..(row + 1) * GLYPH_HEIGHT {
            for x in 0..self.width {
                unsafe {
                    let p = self.base.add(y * self.pitch + x * 4) as *mut u32;
                    p.write_volatile(self.bg);
                }
            }
        }
    }

滚屏为什么敢用 ptr::copy 一次搬？看数据流向：第 1 行搬到第 0 行、第 2 行搬到第 1 行……目的地址永远比源小，从前往后逐字节搬不会覆盖还没搬的数据。ptr::copy 是 memmove 语义，对重叠区间天然安全。这是内核第一次"搬内存"而不只是"写内存"，以后拷贝数据结构处处是它。

第四段：走纸逻辑——打字机的方向盘：

    /// 处理一个字节：'\n' 换行，可打印字符盖章右移，其余忽略
    pub fn put_byte(&mut self, b: u8) {
        match b {
            b'\n' => self.newline(),
            0x20..=0x7E => {
                self.draw_char(self.col, self.row, b);
                self.col += 1;
                if self.col >= self.cols {
                    self.newline(); // 行满自动换行
                }
            }
            _ => {} // 其他控制字符（\t、\r 等）暂不支持
        }
    }

    /// 输出字符串
    pub fn write_str(&mut self, s: &str) {
        for &b in s.as_bytes() {
            self.put_byte(b);
        }
    }

    /// 换行：光标下移一行；已在最底行则滚屏
    fn newline(&mut self) {
        self.col = 0;
        if self.row + 1 < self.rows {
            self.row += 1;
        } else {
            self.scroll();
        }
    }
}

put_byte 是上屏的"入口闸门"：所有字节从这里进，由它决定每个字节该干嘛（换行？盖章？丢弃？）。0x20..=0x7E 正是字模表有图纸的范围。注意屏幕这边 \n 一个字符就完成"回车+换行"（newline 里 col 直接归零）——串口那边要补 \r\n 是两套终端的历史约定差异。

动手四：Makefile——教 make 认识"内核从哪来"

按理说现在就能开机了，但先修一个潜伏已久的问题——不修的话，你会得到一个没有报错、但完全是旧世界的开机结果（怎么发现的，见踩坑实录坑 1）。

问题在 Makefile 这行：

iso: $(KERNEL_ELF)

iso 依赖内核 ELF，但整个文件里没有一条规则告诉 make 怎么造出这个 ELF。make 的逻辑是纯文件时间戳：文件存在、又没有规则说它依赖谁 → 它"永远是最新的" → cargo 永远不会被调用。之前没爆，纯属侥幸：每次都是手动 cargo build 恰好先把 ELF 编新了。

修法是补上"造 ELF"的规则，把依赖说清楚：

# 内核源文件清单：make 靠时间戳决定要不要重编
KERNEL_SRC := $(shell find kernel/src -type f -name '*.rs')

$(KERNEL_ELF): $(KERNEL_SRC) kernel/Cargo.toml kernel/.cargo/config.toml kernel/linker.ld
	cd kernel && cargo build

$(shell find ...) 在 make 启动时列出全部源文件；任何 .rs/Cargo.toml/链接脚本比 ELF 新，就进 kernel 目录编一次。这里有个漂亮的分工：make 管"要不要编"（看文件时间戳），cargo 管"怎么编"（增量编译），两层各司其职。

check 和 clean 目标同步统一成 cd kernel && cargo …——为什么必须 cd 进去而不是 --manifest-path 指过去？坑 3 有答案。

开机：make run

代码全部就位，项目根目录：

make run

屏幕：黑底白字——顶部 === MOS booting ===、hello, screen!，然后满屏 the quick brown fox jumps over the lazy dog。这句"全字母句"（包含全部 26 个字母的英文句子）重复了 60 遍，屏幕只装得下约 48 行，所以你看到的就是滚屏之后的结果——能滚，说明那次大搬运的字节数算对了；算错一丁点，画面会撕裂出半行字。

串口同步打出：

=== MOS booting ===
framebuffer acquired
text drawn

如果屏幕有字但某个字符是方块或错字：字模表下标或位序（最高位对最左像素）反了；如果字整体斜着：pitch 用成了 width × 4——上一章的老坑又长出了新形态。

踩坑实录

坑 1：改了代码，make run 跟没改一样（无报错的静默旧内核）。

本章实际遇到的第一坑，也是最阴的一坑。改完代码跑 make run，画面纹丝不动。查文件时间戳破案：源码 12:28 改的，内核 ELF 还停在 10:38——cargo 根本没被调用，make run 拿旧内核重新打了 ISO（ISO 倒是重打了，因为 iso 是 .PHONY，但材料是旧的）。根因就是动手四讲的：没有规则告诉 make ELF 依赖源码。教训：没有报错≠没有问题，"改动是否生效"要靠输出内容验证，不能只看跑没跑通。

坑 2：make -C kernel 报"没有指明目标并且找不到 makefile"。

修坑 1 时把配方写成 $(MAKE) -C kernel（进 kernel 目录找 Makefile），但 kernel/ 是 cargo 项目，里面根本没有 Makefile。改成直接调 cd kernel && cargo build。

坑 3：duplicate symbol: _start（链接 Linux 程序撞了 libc 的入口）。

中途试过 cargo build --manifest-path kernel/Cargo.toml（从仓库根目录运行），报这个错。诊断线索在报错第一行的路径里：kernel/target/debug/deps——少了 x86_64-unknown-none 这层，编的是宿主 Linux 目标！根因是 cargo 的一个隐蔽规则：.cargo/config.toml 按"当前工作目录"向上查找，跟 --manifest-path 指哪没关系。从仓库根目录跑，读到的是空配置：目标变默认 Linux、没有链接脚本，于是拉了 C 运行时的 _start 跟我们的撞名。所以配方必须 cd kernel && cargo build。诊断技巧送给你：报错里的路径本身就是证据，看一眼 target 下面挂的是哪棵树。

坑 4：Permission denied (os error 13) 写不进 target 目录。

cargo 想覆盖的构建产物属主是别的用户（曾用不同身份编译过）。ls -l kernel/target/.../mos-kernel 一眼可见，sudo chown -R $USER:$USER 项目目录 修好。看到 os error 13，先想想"这文件是谁的"。

本章小结

  • 字模 = 字符的点阵图纸，每字符 16 字节（一行 1 字节，最高位最左像素）；来源不必手写，Linux 控制台字体（PSF）里就是现成的
  • Console 的世界观：像素之上叠字符网格（cols = width/8、rows = height/16），光标只是一个坐标对
  • 盖章要亮暗都画：格子被完整覆盖，无需擦除旧内容
  • 滚屏 = ptr::copy（memmove 语义）一次搬 (rows-1) 行像素
  • make 管"要不要编"（文件时间戳），cargo 管"怎么编"（增量）——两层之间要显式接上依赖
  • cargo 的 .cargo/config.toml 按当前目录向上查找，跨目录构建必须 cd
