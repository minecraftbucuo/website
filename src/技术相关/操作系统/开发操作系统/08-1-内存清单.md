# 08 · 内存管理（一）：拿到内存清单

> 上一章：[07-中断与时钟](07-中断与时钟.md)。内核有了中断——能被时钟叫醒、能接住键盘。
> 但它的内存至今全是编译时定死的：栈是一块 static 数组，光标是一个 static 变量。
> 这一章，给它动态分配内存的能力：运行时申请、用完归还。

本章分五篇，每篇一个独立文件，读完一篇就能跑一篇的验证：

```

08-2-位图分配器.md  位图原理，mm.rs
08-3-发页与收页.md  alloc_frame / free_frame 实验
08-4-内核堆.md      heap.rs、GlobalAlloc、Box/Vec
08-5-踩坑与小结.md  实际踩过的坑，收尾
```

## 这一章要做成什么

到目前为止，内核里所有数据的大小都是**写代码时就定死的**。`BootStack([u8; 64 * 1024])`——64KB，一个字都不能多；想存一个长度未知的字符串？没有出路。可操作系统是要**管理**别的程序的：几个进程、每个多大、打开多少文件——这些数量在写内核时根本不知道。所以内核必须能在**运行时**问内存要空间，用完再还。

本章结束时，内核拥有三层分配能力，从底到顶：

1. **拿到清单**：向 Limine 要一份整机内存清单——哪些物理内存能用、哪些被谁占着
2. **页帧分配**（`mm.rs`）：按整页（4KB）分配物理内存，只能整页整页地给
3. **内核堆**（`heap.rs`）：从页帧分配器拿几页，按任意字节数切分给请求方；再实现 Rust 的 `GlobalAlloc` 接口，`Box`、`Vec` 从此直接可用

要动的东西：

- 修改 `kernel/src/boot.rs`——新增两张 Limine 需求单：`MemmapRequest`（内存清单）、`HhdmRequest`（物理→虚拟的翻译偏移）
- 新建 `kernel/src/mm.rs`——位图页帧分配器
- 新建 `kernel/src/heap.rs`——bump 堆 + `GlobalAlloc` 接线
- 修改 `kernel/src/main.rs`——按顺序接线，加上开机实验

三个模块的分工：

```
boot.rs   向 Limine 递需求单，拿回"内存清单"和"直映射偏移量"
mm.rs     按整页（4KB）分配物理内存；每页的空闲/占用记在位图里
heap.rs   从 mm.rs 拿整页，按请求的字节数切分
              └─ 实现 GlobalAlloc → Box/Vec 的分配自动走到这里
```

每篇先讲原理再写代码。本篇：区段与页 → 两种地址 → 内存清单 → 动手一（`boot.rs` 需求单）→ 动手二（打印清单）。

## 名词速查表

本章的词不像上一章那么多缩写，但几个概念会反复出现，先混个脸熟：

| 词 | 一句话 |
|---|---|
| 物理地址 | 内存条上的真实地址（0x1000 这种） |
| 虚拟地址 | CPU 指令里写的地址，要翻译才落到物理地址上 |
| 页表 | 虚拟地址→物理地址的对照表，硬件（MMU）自动查 |
| 页 / 页帧 | 内存管理的计量单位：全内存等分成 4KB 一格，页号 = 地址 ÷ 4096；“页帧”（frame）强调物理侧 |
| 区段 | region：一段连续的内存范围，清单里的一行——注意跟 07 章分段机制的“段”毫无关系 |
| MMU | Memory Management Unit，CPU 里做翻译的硬件 |
| HHDM | Higher Half Direct Map：全部物理内存按固定偏移镜像到高地址，物理+偏移=可直接用的虚拟地址 |
| memmap | 内存清单：每个区段的起始地址、长度、类型（能用/保留/…） |
| MMIO | Memory-Mapped IO：外设寄存器占用“内存地址”——占的是地址，不是内存条 |
| 位图 | bitmap：1 个比特记 1 页的状态，一整排比特管全部内存 |
| 自举 | bootstrap：鸡生蛋问题——管理内存的工具，自己也要占内存 |
| bump 分配 | 游标只往上顶的分配法：快得像作弊，代价是 free 不回收 |
| GlobalAlloc | Rust 的分配接口 trait：Box/Vec 分配内存时统一调用它；实现它 = 提供内核堆 |

## 原理：内存是怎么被看见的

### 先对齐两个词：区段与页

本章有两个高频词，先掰开——不掰开后面处处卡。

**区段（region）**：一段**连续的内存范围**，"从哪个地址开始、多长、什么用途"。它只是个描述性的说法，不是任何硬件机制。内存清单的每一行，就是一个区段。

> ⚠️ 撞名预警：[07 章](07-中断与时钟.md)讲 GDT 时也有个"段"（segmentation，分段机制）——那是 CPU 的寻址机制，跟这里的"区段"**毫无关系**，纯属中文翻译撞了车。本章凡是说内存，一律用"区段"。

**页（page）**：内存管理的**计量单位**。把物理内存这条长尺**等分**成每格 4096 字节（4KB），一格叫一页；页号就是格子编号，= 地址 ÷ 4096。为什么是 4KB？硬件定的——页表以页为单位翻译地址，不是一字节一字节翻，分配器跟着硬件走：

```
地址:  0x0000    0x1000    0x2000    0x3000    0x4000 ...
         │         │         │         │         │
页号:   第0页      第1页      第2页      第3页      第4页 ...
              每页 4KB（0x1000 字节），等分，无例外
```

两者的关系一句话：**区段是清单上的天然地块（有长有短），页是我们自己画的等分格（全都是 4KB）**。分配器不按区段发货——长短不一没法记账——而是把 usable 区段里的页**逐格**清点。拿清单第一行算笔账：

```
  1000 +86000 usable
```

从地址 `0x1000` 到 `0x87000`，`0x86000 ÷ 0x1000` = 134 页。一行区段 = 一串连续的页。

### 先分清两种地址

第 05 章写显存时，我们拿到的地址长 `0xFFFFFFFF80000000` 这个样子——你可能以为那就是物理地址。不是。x86_64 开了分页模式之后，**CPU 指令里出现的地址全是虚拟地址**，要先经页表翻译成物理地址，才能落到内存条上。翻译是 MMU 硬件自动做的，每个指令访问都查，快到你感觉不到；页表本身是 Limine 在跳进内核之前替我们建好的。

这一章我们**完全不碰页表**（自己建映射是后面章节的事），只需要从 Limine 那里拿到两个现成的东西：

- **HHDM 偏移量**：Limine 建的页表里有一条"直映射"——全部物理内存被按一个固定偏移整体镜像进了高地址。物理地址 + 偏移 = 内核可以直接读写的虚拟地址。第 05 章往显存写字时走的就是这条镜像，只是当时没点名
- **内存清单**：下一节的主角

### 内存不是一整块

你的 QEMU 配了 512MB 内存。直觉上"可用内存"似乎应该是从 0 开始连续 512MB 一整块——拿到清单的那一刻这个想象就碎了。这是实际跑出来的（节选）：

```
memory map:
  1000 +86000 usable              ← 从 0x1000 才开始，第一页被保留了！
  87000 +1000 bootloader reclaimable
  ...
  19D40000 +25000 kernel and modules    ← 我们自己的内核加载在这
  80000000 +3E8000 framebuffer         ← 显存映射
  E0000000 +10000000 reserved           ← MMIO 洞：占地址，不是内存
  FD00000000 +300000000 reserved        ← 又一个 MMIO 洞，12GB "大"
usable total: 1CD MiB
```

为什么长这样？输出里那些 `usable` / `reserved` / … 是每个区段的**类型标签**，标明这段内存是谁在用、还能不能动——现在只需记住一个：**usable = 没有占用者、可以分配的内存**，分配器唯一认的类型。全部 8 种类型的含义，动手一里有一张完整的表。

长成这副碎样子有四个原因，正好对应清单里的几类条目：

- **第一页（0x0~0xFFF）被保留**：这是故意的。空指针的值是 0，如果把 0 地址分出去当正常内存用，程序解引用空指针就会"成功"读到数据、带着错往下跑。保留它，空指针一碰就崩——崩在当场，比错在十万八千里外好查一万倍
- **中间散布着已被占用的区段**：ACPI 电源管理表、固件运行时数据（`ACPI NVS`）、Limine 自己和加载的内核（`kernel and modules`、`bootloader reclaimable`）
- **显存也占地址**：`framebuffer` 区段是显存被映射进了内存地址空间
- **MMIO 洞根本不是内存**：`E0000000` 和 `FD00000000` 起的那两个大区段 reserved，是 PCIe 外设的寄存器窗口——CPU 访问那些地址时，信号根本不去内存条，而是去主板上的设备。它们占用的是**地址**，不是内存条

所以"512MB 的机器"实际能用的是散落在各处、加起来约 461MB 的 usable 碎片。分配器不能"从 0 开始往后发"，必须**只认清单上标了 usable 的区段**——位图分配器就是这么做的（原理在下一篇）。

## 动手一：向 Limine 要清单（boot.rs）

需求单的机制第 05 章见过：一张 `#[repr(C)]` 的单子（接头暗号 + 请求 ID + 回执指针），用 `#[link_section]` 贴到 `.limine_requests` 节区，Limine 启动时扫描、按单备货、把回执指针写回来。内存清单和 HHDM 是两张新单子，**结构跟帧缓冲那张一模一样**，只是 ID 不同、回执内容不同。

先加"内存清单"这张。分三块：单子本体、回执、回执里的条目。

**第 1 块：单子本体**——和 `FramebufferRequest` 逐字段相同，只换了 ID：

```rust
/// 内存映射请求：整机物理内存的区段清单。
/// 结构与帧缓冲请求同构（Limine 所有请求都长这样）
#[repr(C)]
pub struct MemmapRequest {
    magic: [u64; 2],
    id: [u64; 2],
    revision: u64,
    response: UnsafeCell<*mut MemmapResponse>,
}

unsafe impl Sync for MemmapRequest {}

impl MemmapRequest {
    pub const fn new() -> Self {
        Self {
            magic: COMMON_MAGIC,
            id: [0x67cf3d9d378a806f, 0xe304acdfc50c3c62],
            revision: 0,
            response: UnsafeCell::new(core::ptr::null_mut()),
        }
    }

    pub fn response(&self) -> Option<&'static MemmapResponse> {
        let ptr = unsafe { self.response.get().read_volatile() };
        if ptr.is_null() {
            None
        } else {
            Some(unsafe { &*ptr })
        }
    }
}
```

每个字段是干嘛的、为什么 `UnsafeCell`、为什么 `read_volatile`——第 05 章都讲过，不重复。这里只有一处新东西：那对 ID。它不是我们发明的，是 Limine 协议规范给"内存映射请求"写死的编号，抄错一位 Limine 就不认账（回执永远是空指针）。

**第 2 块：回执**——Limine 备好的"取件回执"，内容是一个指针数组：

```rust
/// 内存映射响应：区段指针数组的"取件回执"
#[repr(C)]
pub struct MemmapResponse {
    revision: u64,
    entry_count: u64,
    entries: *const *const MemmapEntry,
}

impl MemmapResponse {
    pub fn entries(&self) -> &[&MemmapEntry] {
        unsafe {
            core::slice::from_raw_parts(
                self.entries as *const &MemmapEntry,
                self.entry_count as usize,
            )
        }
    }
}
```

回执本体在 Limine 的内存里，`entries` 指向一个"条目指针"的数组，每个条目又是一块独立结构体。`entries()` 把这个二级指针包装成 Rust 切片——`from_raw_parts` 第 05 章也用过，套路相同。包装好之后，调用方就能 `for e in resp.entries()` 优雅地遍历了。

**第 3 块：条目**——清单的一行，三个字段说清一个区段：

```rust
/// 一段连续的物理内存区段。
/// 协议里第三个字段名叫 type（Rust 关键字），这里改名 kind
#[repr(C)]
pub struct MemmapEntry {
    pub base: u64,   // 区段起始的物理地址
    pub length: u64, // 字节数
    pub kind: u64,   // 类型：0=可用，其余见 kind_name
}

/// "这段内存是什么"——协议定死的类型值
pub const MEMMAP_USABLE: u64 = 0;

impl MemmapEntry {
    /// 类型值的可读名字（打印日志用）
    pub fn kind_name(&self) -> &'static str {
        match self.kind {
            0 => "usable",
            1 => "reserved",
            2 => "ACPI reclaimable",
            3 => "ACPI NVS",
            4 => "bad memory",
            5 => "bootloader reclaimable",
            6 => "kernel and modules",
            7 => "framebuffer",
            _ => "unknown",
        }
    }
}
```

注意 `base`、`length`、`kind` 都是 `pub`——mm.rs 要直接读它们，这是本章所有代码的原料。类型字段协议里叫 `type`，撞了 Rust 关键字，改名 `kind`（`#[repr(C)]` 管字段顺序和布局，不管字段叫什么名字）。

8 种类型，每一种都是一句实话：这段内存**是谁在用、还能不能动**。开机时固件逐段探测、登记进清单：

| 类型 | 实际含义 |
|---|---|
| usable | 没有占用者的物理内存，内核可以自由分配——**分配器只认这一种** |
| kernel and modules | 我们的内核 ELF 和 Limine 替我们加载的模块所在的内存 |
| bootloader reclaimable | Limine 自己的代码、加载内核时用的临时内存；它把控制权交给内核后不再使用，将来可以改成 usable（本章不处理） |
| framebuffer | 显存的地址映射——第 05 章写入像素的就是这段 |
| ACPI reclaimable | 固件提供的 ACPI 硬件描述表（有几个 CPU、电源按钮接在哪、怎么睡眠）；启动时读一次就够，之后这块内存可回收 |
| ACPI NVS | 固件在系统**运行期间**还要继续使用的 ACPI 数据（睡眠唤醒时要找的），任何时候都不能动 |
| reserved | 固件/硬件保留的地址范围，包括 MMIO 洞（外设寄存器占的地址，不是内存条）；访问它行为未定义 |
| bad memory | 开机探测发现物理损坏的内存，写入的数据会丢失 |

一句话总结：**只有 usable 能分配**；`kernel and modules` 是内核本体；两种 reclaimable 的意思是"占用者已不再需要，将来可回收"（本章不碰）；其余三类一律不碰。

## 动手二：接线，把清单打出来（main.rs）

单子有了，贴出去、等回执。在 `main.rs` 的需求单区（`FRAMEBUFFER_REQUEST` 旁边）加一行：

```rust
/// 内存清单的需求单（08 章：盘点家底）
#[used]
#[unsafe(link_section = ".limine_requests")]
static MEMMAP_REQUEST: boot::MemmapRequest = boot::MemmapRequest::new();
```

然后在 `kmain` 里，串口初始化之后、GDT 之前（内存的事最先办）：

```rust
// 08 章：打印物理内存清单——分配器的原材料目录
match MEMMAP_REQUEST.response() {
    Some(resp) => {
        serial::print("memory map:\n");
        let mut usable_total: u64 = 0;
        for e in resp.entries() {
            serial::print("  ");
            serial::print_hex(e.base);
            serial::print(" +");
            serial::print_hex(e.length);
            serial::print(" ");
            serial::print(e.kind_name());
            serial::print("\n");
            if e.kind == boot::MEMMAP_USABLE {
                usable_total += e.length;
            }
        }
        serial::print("usable total: ");
        serial::print_hex(usable_total / 1024 / 1024);
        serial::print(" MiB\n");
    }
    None => serial::print("no memory map!\n"),
}
```

代码不长，三件事：逐条打印"起始 +长度 类型"（`print_hex` 不带 `0x` 前缀，看输出时自己脑补）；顺手把 usable 区段的长度累加；最后换算成 MiB 打印总量。

### 运行验证

```
make run
```

串口应打印出完整清单（你的数字和这里**可能差几个区段**——OVMF 每次开机自己分配的内存略有不同，清单本身在变，属正常现象）：

```
=== MOS booting ===
memory map:
  1000 +86000 usable
  87000 +1000 bootloader reclaimable
  88000 +18000 usable
  100000 +700000 usable
  ...
  19D40000 +25000 kernel and modules
  ...
  80000000 +3E8000 framebuffer
  E0000000 +10000000 reserved
  FD00000000 +300000000 reserved
usable total: 1CD MiB
```

拿着输出对照原理部分逐行验收：

- **第一个 usable 区段从 `1000` 开始**，不是 0——第一页（0x0~0xFFF）被保留：空指针的值是 0，读它会立刻触发故障，错误当场暴露，而不是带错继续跑
- **usable 不是一整块**：散成好几个区段，中间夹着 ACPI 表、Limine 和内核占用的区段
- **`kernel and modules`**：我们自己的内核 ELF 就加载在这个区段
- **`E0000000` 和 `FD00000000` 两个区段 reserved**：MMIO 洞，加起来比整个内存条还大，但一页都不能当内存发
- **`usable total: 1CD MiB`**：512MB 的机器实际可用约 461MB，缺的去向全在上面各行里

要是打出 `no memory map!`，九成是需求单的 ID 抄错了（回执指针没被填上）；其次是 `#[link_section]` 那行漏了——单子没贴到 Limine 扫描的节区，等于没递。

## 本篇小结

- 指令里写的都是**虚拟地址**，经页表翻译成物理地址；本章不碰页表，靠 HHDM 直映射：物理 + 偏移 = 可直接用的虚拟地址
- 内存清单 = 每个区段的起始/长度/类型；**只有 usable 能分配**；第一页保留是给空指针设的陷阱
- 区段是清单上的连续范围（有长有短），页是 4KB 的等分格（页号 = 地址 ÷ 4096）
