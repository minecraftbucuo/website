# 02 · 第一个内核：让代码编译成"内核文件"

> 上一章：[00-启动流程](00-启动流程.md)。启动链已经理清：Limine 会把
> CPU 交给"内核的第一条指令"。这一章我们就把内核写出来——
> 准确说，是写出它的雏形。

## 这一章要做成什么

一句话：**写一批 Rust 代码，把它编译成一个合法的 64 位内核文件**。

这个内核暂时什么都不干（连输出都没有），但地基必须先立正：它得是一份
Limine 认识的 ELF 文件、住在正确的内存位置、入口正确。之后每一章都是
在这个地基上加盖。

要动 4 个文件（全部新建）：

- `kernel/Cargo.toml`——项目清单
- `kernel/.cargo/config.toml`——编译配置
- `kernel/linker.ld`——内存布局图纸
- `kernel/src/main.rs`——内核本体

全部写完之后 `cargo build` 编译，再用 `file` 和 `objdump` 两个命令
**亲眼查看**编译产物——你会看到自己内核的第一条指令长什么样。

在动手之前，有两件事必须先想明白。

## 先想明白一：内核和普通程序差在哪

你平时写的 Rust 程序，一脚踩在很多"隐形服务"上：`println!` 能打印，
是因为操作系统替它管着屏幕；内存随便申请，是因为操作系统管着内存。
普通程序像住酒店——水电有人供、出错有人兜。

内核没有这个"酒店"。**我们就是在写操作系统**，没有谁能托底。
落到代码上就两条硬规定：

1. **不能用标准库**。`std` 里的每一样东西都依赖操作系统，而我们就是
   操作系统。只能用 `core`——标准库里不碰系统的纯计算部分（整数、
   切片、`Option` 这些）。
2. **没有 `main` 函数**。普通程序从哪开始执行是别人安排的；内核从哪
   开始执行，得我们自己说了算——这就引出了下面的"链接脚本"。

除此之外，`struct`、`match`、所有权、泛型——全部照常。写内核的 Rust
和写应用的 Rust 是同一种语言，只是脚下没有地板。

## 先想明白二：Limine 怎么知道内核放哪、从哪开始

回忆上一章的分工：Limine 负责把内核加载进内存、跳到内核的第一条指令。
它怎么知道往哪放、跳到哪？

答案在内核文件自己身上。内核是 ELF 格式文件，文件内部有一张"装载
清单"（ELF 规范里的程序头表），写着每个部分应该放到内存的哪个地址。
而**装载清单上的地址是谁定的？——是我们，通过一个叫"链接脚本"的
文件**。Limine 只负责照单执行。

于是第一个思考题有了答案：链接脚本就是内核的**装修图纸**——规定
代码放哪个地址、数据放哪个地址、入口是哪个函数。这是本章要写的
第一个文件。

第二个思考题：内核的第一条指令，为什么不能用 Rust 写？

因为任何 Rust 函数编译出来的开头都有一段"例行手续"：把寄存器存进
**栈**、调整栈指针。可 Limine 交权的时候，栈指针指向哪里是不确定的
——Rust 例行手续一执行就踩空。所以第一条指令必须是几行汇编：
**先亲手把栈立起来，再 call 进 Rust 世界**。这也是本章 main.rs 里
最核心的一段代码。

## 动手一：项目清单与编译配置

```toml
# kernel/Cargo.toml
[package]
name = "mos-kernel"
version = "0.1.0"
edition = "2024"

# 内核不支持栈展开（那需要操作系统配合），
# panic 时直接停机，不走展开流程
[profile.dev]
panic = "abort"

[profile.release]
panic = "abort"
```

```toml
# kernel/.cargo/config.toml
# cargo 每次编译自动带上这里的配置，免得命令行敲一长串

[build]
# 编译目标：x86_64 裸机（无操作系统版本）。
# 它的核心库官方有预编译版，stable 工具链直接可用
target = "x86_64-unknown-none"

[target.x86_64-unknown-none]
rustflags = [
    # 链接时用我们自己的图纸
    "-C", "link-arg=-Tlinker.ld",
    # 静态重定位：内核地址链接时就定死。
    # 这个目标默认开启 pie（地址不定、随处可放），那是给普通
    # 程序的待遇，内核用不着，还会跟高地址布局打架
    "-C", "relocation-model=static",
]
```

两个配置文件各管一件事：`Cargo.toml` 说"这是什么项目"，
`.cargo/config.toml` 说"用什么姿势编译"——目标选了 `x86_64-unknown-none`
（裸机版，没有标准库依赖），链接用我们的图纸，地址定死不搞"随处可放"。

顺带讲清 `edition = "2024"` 这行，它跟"用多新的编译器"无关。Rust 有条
独特承诺：**老代码永远能编译**。可语言又不能不改进——有些旧写法必须
废弃。两头兼顾的方案就是 edition（方言）：2015 / 2018 / 2021 / 2024，
同一个编译器四种都认，crate 各选各的。2024 方言对内核最有用的两条：
**危险属性必须写 `#[unsafe(...)]`**、**禁止对 `static mut` 取普通引用**
（下一章起新代码里那些"看着多余"的写法，源头都在这）——相当于让
编译器强制把关现代 Rust 的安全纪律。我们全程只用 stable 编译器，
这跟 edition 是两码事，别混。

## 动手二：linker.ld——内存布局图纸

链接器的工作是把编译产物拼装成最终文件，拼之前它需要图纸。写
`kernel/linker.ld`：

```ld
/* 内核链接脚本——规定各部分放在哪些虚拟地址 */

ENTRY(_start)                  /* 入口符号：Limine 跳转到 _start */

KERNEL_BASE = 0xFFFFFFFF80000000;

SECTIONS
{
    /* '.' 是"当前位置计数器"，拨到内核基址，
       后面所有节从这个虚拟地址开始排布 */
    . = KERNEL_BASE;

    /* 代码段：入口代码排最前 */
    .text : ALIGN(4K) {
        KEEP(*(.text.entry))   /* KEEP: 防止链接器把没人调用的入口删掉 */
        *(.text .text.*)
    }

    /* 只读数据：字符串常量等 */
    .rodata : ALIGN(4K) {
        *(.rodata .rodata.*)
    }

    /* 已初始化的可写数据 */
    .data : ALIGN(4K) {
        *(.data .data.*)
    }

    /* 未初始化数据：不占文件体积，加载时清零 */
    .bss : ALIGN(4K) {
        __bss_start = .;
        *(.bss .bss.*)
        __bss_end = .;
    }

    . = ALIGN(4K);
    KERNEL_END = .;            /* 内核结束地址，以后内存管理要用 */

    /* 丢弃用不到的节，减小体积 */
    /DISCARD/ : {
        *(.eh_frame*)
        *(.note*)
        *(.comment*)
    }
}
```

逐块看。编译器产出代码时会按性质分箱：机器码装进 `.text` 箱，
字符串常量装进 `.rodata` 箱，有初值的变量装进 `.data` 箱，没初值的
装进 `.bss` 箱。链接脚本规定这些箱子在内存里各住哪一层。

**为什么基址是 0xFFFFFFFF80000000（64 位地址空间的顶楼）？**
一楼将来整层租给用户程序，内核自己住顶楼，两边永不争地盘——Linux
的内核基址恰好也是这个数，我们沿用这个门牌。"顶楼这么大，物理内存
没那么多住得下吗？"住得下——这是**虚拟地址**，不是真实门牌；中间
有"页表"这位翻译员把它翻译成真实住址，而 Limine 启动时已经把翻译表
建好了。

**`ALIGN(4K)`** 让每个节都从 4KB 的整数倍开始——4KB 正是内存页的
大小，页对齐的内核后面管理起来省无数事。

## 动手三：main.rs——立栈，进入 Rust

新建 `kernel/src/main.rs`。整份文件不长，但每一段都值得细看：

```rust
// 不链接标准库：没有操作系统托底
#![no_std]
// 没有 main：入口由链接脚本的 ENTRY(_start) 决定
#![no_main]

use core::arch::naked_asm;
use core::panic::PanicInfo;
```

`#![no_std]` 和 `#![no_main]` 是前面两条硬规定在代码里的样子。

```rust
/// 内核启动栈。
/// #[repr(align(16))]：x86-64 规定栈必须 16 字节对齐，
/// 否则某些指令会触发对齐错误——裸机开发经典的隐形坑
#[repr(align(16))]
struct BootStack([u8; 64 * 1024]);   // 64 KiB，启动阶段够用

// 放进 .bss 段：不占文件体积，Limine 加载时清零
static BOOT_STACK: BootStack = BootStack([0; 64 * 1024]);
```

这就是"第一条指令不能用 Rust"的答案里要立的东西：一块 64KB 的
内存当栈用。栈是函数调用的基础设施——每次调用压返回地址、存局部
变量都靠它。

```rust
/// 内核的第一条指令。
#[unsafe(no_mangle)]                        // 符号名保留为 _start，不被改名
#[unsafe(link_section = ".text.entry")]   // 钉进图纸里的入口节（代码段最前）
#[unsafe(naked)]                            // 裸函数：不生成任何例行手续
pub extern "C" fn _start() -> ! {
    naked_asm!(
        // 先把栈的起始地址装进 rax。movabs 装 64 位立即数，
        // 装得下高地址——lea 的 32 位寻址装不下（坑 2 会讲）
        "movabs rax, {stack}",
        // rsp 指向栈的"末尾"：栈从高地址向低地址生长
        "lea rsp, [rax + 64*1024]",
        // 清零帧指针：栈回溯到此为止（没有上层调用者）
        "xor ebp, ebp",
        // 进入 Rust 世界。call 压入返回地址，Rust 函数从此有栈可用
        "call {kmain}",
        // 万一 kmain 返回了（不该发生），停机死循环兜底
        "2:",
        "hlt",
        "jmp 2b",
        stack = sym BOOT_STACK,   // sym：把符号地址嵌进汇编
        kmain = sym kmain,
    );
}
```

三个属性各管一件事：`no_mangle` 让函数名保持 `_start` 不被 Rust 改名
（链接图纸里写的是这个名字）；`link_section` 把它钉进 `.text.entry`
（图纸规定入口排最前）；`naked` 是"裸函数"——**编译器不许给这个函数
生成任何例行手续**，函数体里的汇编就是全部。没有 naked，编译器生成的
例行手续会在栈还不存在时就用栈，当场踩空。

汇编一共五步：把栈地址装进 `rax` → 算出栈顶装进 `rsp`（栈向低地址
生长，所以指向数组末尾）→ 清帧指针 → `call` 进 Rust → 兜底死循环。
第 5 章会再见到 `{stack}`/`sym` 这类"把符号嵌进汇编"的写法。

```rust
/// Rust 世界的入口。目前什么都不做
#[unsafe(no_mangle)]
pub extern "C" fn kmain() -> ! {
    loop {
        core::hint::spin_loop();
    }
}

/// no_std 的强制要求：标准库的 panic 逻辑没了，得自己接盘。
/// 现在是死循环，后面升级成"打印错误位置并停机"
#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    loop {
        core::hint::spin_loop();
    }
}
```

`kmain` 是汇编 `call` 的去处，Rust 世界从它开始。`#[panic_handler]`
是编译器的硬性要求：程序出错时总得有个去处，标准库那套依赖操作系统，
我们只能自己提供一个——哪怕是死循环。

## 编译与验证

先做一次性准备（下载裸机目标的预编译核心库），然后编译：

```fish
rustup target add x86_64-unknown-none   # 一次性

cd ~/Desktop/MOS/kernel
cargo build
```

编译产物在 `target/x86_64-unknown-none/debug/mos-kernel`。用两个命令
检查它：

```fish
file target/x86_64-unknown-none/debug/mos-kernel
```

期待输出里有 `ELF 64-bit LSB executable, x86-64, statically linked`——
它是 64 位、静态链接的 ELF 文件。再用反汇编看它的开头：

```fish
objdump -d target/x86_64-unknown-none/debug/mos-kernel | head -12
```

你会看到（地址可能略有出入）：

```
ffffffff80000000 <_start>:
ffffffff80000000:  48 a1 ...  movabs 0xffffffff80001000,%rax   ← 栈地址进 rax
ffffffff8000000a:  48 8d ...  lea    0x10000(%rax),%rsp        ← rsp = 栈顶
ffffffff80000011:  31 ed      xor    %ebp,%ebp
ffffffff80000013:  e8 ...     call   ffffffff80000020 <kmain>  ← 进入 Rust
ffffffff80000018:  f4         hlt                               ← 兜底
```

对照着看：`_start` 正好落在图纸规定的 `0xffffffff80000000`；右边
是我们写的五步汇编，左边是它对应的真实机器码。**图纸、汇编、机器码
三者在这一刻对上了号**——这就是本里程碑的验证标准。

## 踩坑实录

**坑 1：`unsafe attribute used without unsafe`。**

```
error: unsafe attribute used without unsafe
   |
29 | #[naked]
   |   ^^^^^ usage of unsafe attribute
```

`#[naked]`、`#[no_mangle]`、`#[link_section]` 这类属性能绕过编译器的
常规保证（不改名、挪位置、不加前置代码），Rust 把它们归为"危险属性"，
必须写成 `#[unsafe(naked)]`——和 `unsafe {}` 块同一个思想：**危险的
地方必须写得扎眼**。这条规矩在 edition 2021 里只是提示，**edition 2024
起升级为强制**。本项目后来从 2021 切到 2024 时就被它抓了现行：代码里
还剩两处没包 `unsafe` 的 `#[link_section]` 和 `#[no_mangle]`，切过去
当场报错——危险属性强制显式化的好处，就是漏网之鱼一个都跑不掉。

**坑 2：`relocation R_X86_64_32S cannot be used`（链接错误）。**

先解释"重定位"：链接器拼装时，要把代码里"这里填某符号地址"的占位符
替换成真实地址，`R_X86_64_32S` 表示这个占位符只有 **32 位宽**。
我们的内核住在 64 位的高地址，`lea rsp, [栈地址]` 这种 32 位寻址
根本装不下。另外链接命令默认带 `-pie`（"随处可放"模式），跟定死
地址的内核冲突。

修法两处：汇编改成先用 `movabs`（专装 64 位立即数）把地址搬进
`rax`，再 `lea rsp, [rax + 64*1024]`；配置里加
`-C relocation-model=static` 关掉 pie。

> **经验**：裸机开发一半的报错都是"地址宽度 / 对齐 / 加载位置"问题。
> 见到重定位错误，先问：这个数装得下吗？对齐了吗？链接地址和加载
> 位置一致吗？

## 本章小结

- 内核 = 没有酒店的程序：`no_std`（无标准库）、入口自定义（图纸说了算）
- 链接脚本是内存布局图纸；"高地址内核"是主流 OS 的通用布局
- 第一条指令必须是汇编：立栈 → `call kmain` 进 Rust
- `file` 看格式、`objdump -d` 看反汇编——这两个命令以后天天用

**里程碑**：`cargo build` 产出高地址、静态链接的 64 位内核 ELF，
反汇编可见五步入口指令 ✅
